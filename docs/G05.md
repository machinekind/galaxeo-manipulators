# G0.5 on the A1X

The plan for running Galaxea's G0.5 model on our A1X arm. Pick-and-place comes
first. Pouring comes second. Every stage has a gate. We do not pay for the next
stage until the gate passes.

## Decision

We fine-tune G0.5 on planner demonstrations from our simulator and deploy the
result on the real A1X. The scripted planner stays the teacher. The calibrated
top-down map and the ACT policy are parked. They come back only if G0.5 fails
to transfer.

## What G0.5 is

G0.5 is a vision-language-action model from Galaxea. It takes camera images, a
text instruction and the joint state, and it outputs joint targets. One
transformer writes a short plan, then the action tokens, in one stream. It
starts from a 2B vision-language model, so it already recognises everyday
objects. Its bounding box for the target object is printed before it moves.

The weights are public at https://huggingface.co/OpenGalaxea/G05. The code is
at https://github.com/OpenGalaxea/GalaxeaVLA. The paper is
https://arxiv.org/abs/2608.11739.

There is no A1X in the model. The repo has a recipe for the SO-100 hobby arm,
which is a single arm with one external camera and one wrist camera, joint
position actions and a gripper. We copy that recipe.

## Why pick-and-place first

The model's robot pretraining is mostly pick-and-place. Its own benchmark is
"pick the named object among distractors and put it in the named container".
Our target task is "take the cookie and put it on the legged robot". That is the
same task with a new container. The pour is a wrist roll the model has never
seen. So pick-and-place has the best odds and proves the A1X embodiment. The
pour then reuses everything.

## Stage 0. Motion gap check

The real arm is position controlled and the model outputs joint targets, so the
motion side of sim-to-real should be small. We check it before anything else.

1. Run one planner pick-and-place episode in sim and save its action stream.
2. Replay that stream on the real A1X, open loop, with no objects on the table.
3. Compare the measured joints against the sim trajectory.

Gate: the real arm traces the sim path at the same speed. Gripper closing time
and force are the likely mismatches. We fix those in the sim before recording
data.

## Stage 1. Dataset from sim

The planner in `sim/planner/pickplace.py` produces the demonstrations. The
dataset is LeRobot v3, the same format the recorder on the real arm writes.

Schema:

| key | shape | meaning |
| --- | --- | --- |
| `action` | (7,) | target joints in radians, plus gripper |
| `observation.state` | (7,) | measured joints in radians, plus gripper |
| `observation.images.laptop` | 240 x 320 x 3 | the randomly placed external camera |
| `observation.images.wrist` | 240 x 320 x 3 | the wrist camera |

The G0.5 loader routes any image key containing "wrist" to the wrist slot and
every other image key to the external slot. So the pick-and-place dataset
carries `laptop` and `wrist` only. The top-down map is left out.

Randomised per episode: object shapes and colours, object count and positions,
dog pose and sway, camera pose and intrinsics, lighting, table texture and
colour, background, distractors. The last four are new and belong in the scene
builder before the dataset is generated.

Size: 300 successful episodes at 20 Hz. That matches the pour set and is what
the SO-100 recipe was built for.

Gate: a dataset with 300 episodes, each camera stream decodes, and the joint
ranges match the real arm.

## Stage 2. Fine-tune on Vast

Hardware: one 80 GB GPU. A100 80 GB, H100 80 GB or H200. A CUDA 12.8 developer
image with PyTorch 2.7.1 cu128, since flash-attn 4 builds natively. Python 3.10.
About 100 GB of disk. Around 1 to 3 dollars per hour.

Steps on the box:

1. Clone GalaxeaVLA and run `uv sync`.
2. Download `g05-base`, the action tokenizer and the processor. About 12 GB.
   Skip the other checkpoints.
3. Upload the dataset as one tar, the way `sim/jobs/dataset.sh` does it.
4. Add `configs/data/a1x.yaml` and `configs/task/a1x.yaml`, copied from the
   SO-100 files. Change the state and action shape from 6 to 7, set the
   embodiment type to `a1x`, set the fps to 20, and point the dataset directory
   at our upload.
5. Compute the stats file with `tests/test_dataloader_batch.py`. It is
   computed on the box from the dataset.
6. Run the smoke test: `bash scripts/run/finetune.sh 1 a1x --test`. It runs two
   steps and proves the data, the checkpoint and the loss all load.
7. Run the real fine-tune: `bash scripts/run/finetune.sh 1 a1x`. The SO-100
   defaults are 4 epochs, batch 16, learning rate 8e-5. We lower the backbone
   learning rate multiplier so the sim images do not overwrite the pretrained
   vision features.
8. Copy the checkpoint off the box during training, not only at the end.

Cost of one attempt: about 10 to 15 dollars. Two hours of setup the first
time, then three to five hours of training.

Gate: training loss falls and the checkpoint loads in the policy server.

## Stage 3. Offline photo test

Before the arm moves, we test the vision on real frames.

1. Take twenty photos with the real laptop camera: our table, a few objects,
   the dog, several camera positions.
2. Run the fine-tuned model on each photo with the instruction "pick up the X".
3. Read the bounding box it emits in its plan.

Gate: the box lands on the named object in most photos. If it does not, vision
did not transfer and the arm stays off. We go back to Stage 1 randomisation, or
to the Cosmos stage below, and fine-tune again.

## Stage 4. A1X client and real rollouts

The policy server runs on the GPU box. The client runs on the laptop next to
the arm. The SO-100 client is one Python file that reads cameras and joints,
sends them over a WebSocket, receives an action chunk and executes it. We copy
that file and replace its serial arm class with our CAN arm class from
`so101_bridge.py`. The WebSocket helper in `scripts/utils` is reused as is.

Joint units stay in radians on both sides, because that is what the dataset
uses. The client keeps its per-tick step limit as a safety guard. The
instruction is a text string, so "pick up the cookie and put it on the dog" is
the whole task spec.

Inference needs a GPU with 8 GB or more, so a cheaper Vast instance or a local
card.

Gate: ten rollouts on the real arm, scored by hand. We record every rollout
with the recorder, success or not.

## Stage 5. Close the pixel gap

If Stage 4 is weak, the model is failing on real pixels. The levers, cheapest
first:

1. More visual randomisation in sim. Lighting, textures, backgrounds, camera
   intrinsics, distractors.
2. Composite sim renders over real photos. Render the arm and objects with a
   transparent background and paste them onto frames from the real laptop
   camera. Two days of work.
3. Keep the backbone learning rate low so the pretrained real-image features
   survive.
4. Prefer the wrist camera. It sees the gripper and the object against a small
   patch of table, which is easier to match than a whole room.
5. Co-train with a small real set. Twenty to fifty real episodes mixed into the
   sim set. The real episodes are spread over several tables, camera positions
   and objects, so the model learns what a real camera looks like in general. They
   come from the SO-101 leader teleop, or from the planner on the real arm.

The real set is collected once. A new table or a new camera position needs no
new data. If a new setup fails the photo test, we add a handful of episodes
from it, once.

The loop after that is the DAgger loop the tooling already implements: run the
policy, log failures, take over with the planner or the leader arm, co-train,
repeat.

## Optional. Cosmos

NVIDIA Cosmos Transfer turns depth, segmentation and edge maps from the sim
into photorealistic video. A text prompt sets the table, the light and the
clutter. The objects do not move, so the actions still line up with the frames.
MuJoCo renders depth and segmentation, so the scene builder can save them next
to the RGB.

We try it only after a plain sim baseline exists. Then we generate one
Cosmos-augmented copy of the same dataset, fine-tune again, and run the same
photo test. If the box-on-object rate jumps, we keep it.

Cost: one 80 GB GPU, tens of GPU hours per augmented copy, so tens of dollars.
A few days of setup for the model weights and the map export.

Known limits: the output looks real, but the lens, noise and colour of our webcam are missing. Thin
things and the gripper contact can be redrawn wrong. We check wrist frames by
eye.

## Then the pour

Once pick-and-place works on the real arm, the pour is a second dataset. The
pour scene, its planner and 300 sim episodes exist already. We add the pour
set to the pick-and-place set and fine-tune once more, so one checkpoint does
both tasks. The pour motion comes only from our demonstrations, so its
sim-to-real gap is the one to watch.

## Open questions

- How the model uses the embodiment name. The config takes any string, and the
  SO-100 recipe used a new one, so `a1x` should work. The smoke test confirms.
- Whether the SO-100 dataset loader accepts a 7-dim state without code changes.
  The shape is a config value, so it should.
- Whether 20 Hz or 15 Hz is better for the A1X. The SO-100 recipe used 15 Hz.
  We keep 20 Hz to match the existing datasets and revisit if control looks
  jerky.
- How many real episodes the SO-100 fine-tune used. Galaxea does not say.
